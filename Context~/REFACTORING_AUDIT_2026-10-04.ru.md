# WhimTex: рефакторинг для работы агента

Дата пересмотра: 4 октября 2026 года. Цель — сократить поиск зависимостей, повторные правки и подготовку проверок, а не привести проект к абстрактному Clean Code.

## Итог

Из оставшихся R05–R15 оставлены **три задачи**, причём две существенно сужены:

| Порядок | ID | Проблема → решение | Что это упрощает агенту |
| --- | --- | --- | --- |
| 1 | R14 | Протокол запуска тестов нужно восстанавливать → явные сценарии и один runner | Повторить проверку и отличить завершённый pass от успешного запуска |
| 2 | R05 | Общие правила batch обслуживаются в нескольких циклах → один исполнитель операций и общей валидации | Менять правила batch без параллельного редактирования трёх входов |
| 3 | R09 | Временное состояние рендера вручную сохраняется и восстанавливается в разных местах → небольшой scope | Проверить изоляцию вызова без повторного разбора всех save/restore-блоков |

R06, R07, R08, R10, R11, R12, R13 и R15 сняты с текущего плана. Это не список «сделать позже»: возвращаться к ним стоит только при конкретной задаче или новом доказательстве пользы.

R01–R04 уже выполнены локально. Реализация и границы предыдущего прогона сохранены в [отчёте R01–R04](https://github.com/DCFApixels/WhimTex/blob/ca8603c0961ce36064280f952259f8a6142d46cc/Tests~/Legacy/RefactoringR01R04.ru.md). В этом пересмотре изменена документация, не производственный код; Unity, тесты и профилирование не запускались.

После пересмотра **R14 реализован локально**: [инструкция](../Tests~/RUNNING_TESTS.md), [проверки и границы пилота](https://github.com/DCFApixels/WhimTex/blob/ca8603c0961ce36064280f952259f8a6142d46cc/Tests~/Legacy/TestRunner.ru.md). Каталог намеренно частичный; это не перенос всего исторического набора. R05 и ограниченный R09 пока не выполнялись. Описание ниже сохраняет обоснования отбора; будущими задачами остаются только эти два пункта.

## Критерий отбора

Предложение оставлено, если в текущем коде видно хотя бы одно конкретное препятствие:

- Одно правило приходится независимо поддерживать в нескольких местах.
- Для локальной правки нужно восстанавливать скрытые условия вызова или владение состоянием.
- Проверку нельзя повторить по известному описанию без ручного выяснения протокола.

Размер файла, число partial-файлов, наличие reflection по собственным типам или отсутствие отдельного «сервиса» сами по себе не проблема. Новый слой полезен только тогда, когда сокращает обязательные места правки или проверки; универсальная система с дополнительными исключениями может ухудшить работу агента.

Это оценка по исходникам и истории проверок, а не измерение экономии времени или контекста.

## R14. Неочевидный запуск тестов → воспроизводимые сценарии

**Проблема → решение.** Проверки используют разные runners, entry points и способы завершения. Зафиксировать сценарии в небольшом машинном каталоге и запускать через одну процедуру.

**Причина → действие.** Сейчас перед прогоном агент выясняет, нужен ли `run_script` или `eval_file`, какой метод вызывать, нужно ли ждать и что означает результат. Это повторяется при каждом рефакторинге → отделить описание запуска от исторического отчёта и эвристик по исходникам.

Подтверждение:

- [audit-sources.mjs](https://github.com/DCFApixels/WhimTex/blob/ca8603c0961ce36064280f952259f8a6142d46cc/Tests~/Legacy/scripts/audit-sources.mjs) ищет методы регулярными выражениями и эвристически классифицирует файлы. Это полезная инвентаризация, но не исполняемый контракт сценария.
- [LayerPreviewReuseSmoke.cs](https://github.com/DCFApixels/WhimTex/blob/ca8603c0961ce36064280f952259f8a6142d46cc/Tests~/Legacy/LayerPreviewReuseSmoke.cs): `Start` возвращает «Started», выполнение отложено, финальный `Result` может быть `Running`, `Passed` или `FAILED`.
- [Результаты R01–R04](https://github.com/DCFApixels/WhimTex/blob/ca8603c0961ce36064280f952259f8a6142d46cc/Tests~/Legacy/RefactoringR01R04.results.json) уже содержат file/entry/runner/args и результаты. Их можно использовать как исходный материал, но журнал выполненного прогона не задаёт полный протокол следующего.
- [Отчёт R01–R04](https://github.com/DCFApixels/WhimTex/blob/ca8603c0961ce36064280f952259f8a6142d46cc/Tests~/Legacy/RefactoringR01R04.ru.md) фиксирует сбой нового теста из-за неверного индекса JObject-аргумента в reflection. Это издержка подготовки проверки, а не дефект проверяемого encoder.

Конкретные действия:

1. Описать для каждого включённого сценария файл, runner, entry/args, prerequisites, побочные действия, cleanup, timeout и способ распознавания финального результата. Для async — отдельный entry завершения.
2. Начать с воспроизводимого набора из последнего прогона; добавить небольшие профили по подсистемам. Явно перечислить невключённые диагностические и ручные сценарии, не называть частичный профиль полным набором.
3. Runner должен различать ошибку транспорта, внутренний `success:false`, провал assertions, незавершённый async, timeout и SKIP. Диагностическое измерение не считать поведенческой регрессией.
4. Перед запуском по-прежнему читать исходник каждого выбранного теста: каталог не заменяет проверку безопасности и не даёт разрешения менять ассеты или настройки.
5. Если повторяющееся обращение к package-owned internal API действительно требует общего helper, проверять точную сигнатуру и выдавать понятную ошибку. Не переносить всю reflection механически в адаптер и не добавлять test bridge в production без отдельной необходимости.
6. Сохранить машинный итог с окружением и фактически завершёнными сценариями; результат должен воспроизводиться из каталога, а не из памяти предыдущего агента.

**Что не делаем:** новую тестовую платформу, массовый перенос в другую assembly, auto-run при открытии проекта или новый доступ к закрытым Unity API.

**Польза агенту:** меньше ручной подготовки; по результату видно, сломано поведение, тестовый вызов или инфраструктура. Это самый прямой выигрыш из оставшегося плана.

**Проверка будущей реализации:** failing inner result, неверная сигнатура, async failure/timeout, SKIP, cleanup при исключении и повтор выбранного профиля в нужном Editor. Только штатная Unity-компиляция; player build не нужен.

## R05. Несколько batch-циклов → одна общая середина

**Проблема → решение.** Обход операций, aliases, per-operation response и итоговые проверки повторены в нескольких API-входах. Расширить существующий `RunCommonOperations`, не создавать отдельный framework исполнения.

**Причина → действие.** Чтобы изменить общую batch-валидацию или диагностику, агент должен сопоставлять несколько реализаций → оставить эти правила в одном месте, а жизненный цикл каждой транзакции у её владельца.

Подтверждение:

- [WhimTexApi.cs](../src/Automation/WhimTexApi.cs): отдельные probe/apply-циклы; в probe отдельно подсчитываются слои и Drawing pixels, в apply вызывается `ValidateAgentBudget`.
- [WhimTexApi.AssistantBatch.cs](../src/Automation/WhimTexApi.AssistantBatch.cs): существующий `RunCommonOperations` и общая бюджетная проверка.
- [WhimTexApi.TiffLive.cs](../src/Automation/WhimTexApi.TiffLive.cs): `ReplayTiffLiveRequest` повторяет aliases, обход, построение результатов и итоговую валидацию.
- [WhimTexApi.Layers.cs](../src/Automation/WhimTexApi.Layers.cs): `ApplyOperation` уже общий.

**Поправка к исходному аудиту:** новая операция сама по себе не требует править три цикла — dispatch уже централизован. Польза этого пункта именно в сопровождении общих batch-правил, а не в количестве обработчиков операций.

Конкретные действия:

1. Один исполнитель управляет aliases, порядком `ApplyOperation`, индексом текущей операции и, когда нужно, сбором её результата.
2. Общие target/budget-проверки вызываются из одного места с явным document path. Сохранить phase-specific сведения об ошибке и частичных результатах.
3. Сначала зафиксировать нынешние различия: assistant обновляет transform hierarchy после каждой операции, другие циклы не делают этого явно. Не объявлять это ошибкой и не удалять обновления без проверок зависимых операций.
4. Probe остаётся `execute:false`; создание копии, Undo/rollback, сохранение и обработка save failure остаются в конкретном workflow.
5. TIFF replay сохраняет baseline, requestId/retry и замену working model только после успешной подготовки. Не превращать повтор запроса в повтор добавлений или stroke.

**Что не делаем:** общий транзакционный движок, объединение независимой TIFF-сессии с оконной, множество strategy-классов или режимов ради устранения нескольких строк.

**Польза агенту:** меняя лимит или формат ошибки batch, достаточно проверить общий алгоритм и небольшие внешние обвязки. Если для извлечения понадобится множество callback/options, остановиться: такая версия перестанет соответствовать цели.

**Проверка будущей реализации:** AgentEditingSmoke, AgentResizeSmoke, TiffLiveSmoke, LiveAgentSmoke; aliases, зависимые операции, ошибка в середине, dry-run без побочных действий, rollback, requestId и save failure. Различия транзакций должны оставаться видимыми в тестах.

## R09. Повторное сохранение render state → небольшой scope

**Проблема → решение.** Некоторые пути вручную сохраняют поля композитора и GPU state, временно меняют их и восстанавливают в `finally`. Собрать повторяющийся контракт восстановления в маленькую обвязку.

**Причина → действие.** При правке такого пути агент должен помнить, какие поля временные, что нужно вернуть при исключении и какие результаты остаются после рендера → явно отделить временное состояние от опубликованного результата и владения ресурсами.

Подтверждение:

- [RenderCanvasWithCache](../src/TextureCompositor.EffectCache.cs): временные `effectCache`, `interactiveEffects`, `publishingLayerPreview`.
- [RenderLayerThumbnail](../src/TextureCompositor.Thumbnails.cs) и [PickLayerAtPixel](../src/TextureCompositor.LayerPicking.cs): повторяющееся сохранение cache, quality, diagnostics и `RenderTexture.active`.
- [RasterizeFXPrefix](../src/TextureCompositor.ApplyFX.cs): свой save/restore cache и quality.
- [RenderCanvasCore](../src/TextureCompositor.cs): отдельно владеет локально созданным cache и temporary output; это нельзя механически заменить той же логикой освобождения.

Нынешние `finally` уже восстанавливают состояние. Здесь не обнаружен новый сломанный путь.

Конкретные действия:

1. Зафиксировать список временных полей и их восстановление в небольшом scope без allocations на горячем пути.
2. Подключать только подходящие entry points; не заставлять все виды рендера иметь одинаковые настройки.
3. Не откатывать `lastLayerPreview*` как временные поля: это опубликованный результат успешного Canvas render. Не смешивать их с `publishingLayerPreview`.
4. Scope восстанавливает состояние, но не уничтожает borrowed cache или возвращённую текстуру. Владение temporary/persistent ресурсами остаётся явным у caller.
5. Проверить nested calls и исключения, прежде чем расширять применение обвязки.

**Что снято из первоначального R09:** новый универсальный `RenderRequest`, перенос runtime-ресурсов в `CanvasRenderer` и переписывание pipeline. Их самостоятельная польза агенту пока не доказана.

**Польза агенту:** новый изолированный render-путь можно сверить с одним контрактом восстановления; не нужно копировать и заново проверять список полей в нескольких `finally`.

**Проверка будущей реализации:** RenderStateSmoke, LayerPreviewReuseSmoke, EffectCacheSmoke, CanvasRenderNamingSmoke; исключения/nested state, clipping/group/Target, picking/thumbnail/export. Миниатюры сохраняют отключённые transform/clipping и разрешённый hidden layer.

## Что снято и почему

| ID | Исходное предложение | Почему не оставлено ради работы агента |
| --- | --- | --- |
| R06 | Общая метаинформация binary/JSON fields | Оба reader уже автоматически находят поля. Различаются границы допустимых типов, exclusions и файловые политики. Общий каталог добавит механизм и исключения; конкретная повторяемая задача, которую он заметно упрощает, не показана. |
| R07 | Descriptor простых API-параметров | Setter и snapshot Noise находятся рядом; enum-схема уже читает исходник. NoiseContract проверяет keys/snapshot/schema, MakeSeamlessContract — также числовые bounds. Новый descriptor связывает C#, JS и UI и требует освоения отдельного механизма. Дополнить конкретный contract-test при изменении поля дешевле, чем заранее переписывать параметры. |
| R08 | Выделение UI-компонентов из окна | Partial-файлы уже дают навигацию; CreateGUI и OnEnable/OnDisable показывают lifecycle. Новые Bind/Refresh/Dispose и owner-context потребуют распределить Undo, selection, ввод и refresh между объектами. Для оставшегося плана нет конкретной локальной задачи, оправдывающей этот перенос. |
| R10 | Индекс дерева слоёв | Текущие Find/TryFind уже централизованы и читаемы. Индекс добавит правила инвалидирования после структурных изменений/Undo; это преимущественно оптимизация, не сокращение обязательного контекста агента. |
| R11 | Инкрементальное обновление строк UI | Неизменённая структура уже обновляет значения без пересборки. Diff строк добавит rebind старого Behaviour, focus и drag/drop-состояния. Без конкретной проблемы это усложнит локальные UI-правки. |
| R12 | Отдельный сервис revision и кеширование | Revision уже собрана в одном методе, фильтрация derived FX — рядом. Вынос сам по себе не уменьшит число мест правки, а кеш потребует новых правил инвалидирования pixels/Undo. Это отдельная задача производительности. |
| R13 | Типизированные effect stamps вместо JSON | Общий Stamp сейчас получает сериализуемые значения автоматически. Ручные stamps добавят место, которое агент должен помнить при каждом новом поле, и риск stale cache. Без замеров такое изменение скорее мешает. |
| R15 | Переписывание Live Update в state machine | Существующие guards явно учитывают save pause, pending import и durable recovery journal. Новый enum не отменяет эти условия. При конкретной правке сессии полезно описать переходы и проверить их, но отдельная переделка всей реализации сейчас не оправдана. |

Для R08 проверены существующие UI Toolkit границы с использованием навыка `ui-uitk`. Это повлияло на решение сохранить текущую структуру: компоненты не выделялись, appearance и bindings не менялись.

## Границы следующего этапа

- Сохранить чтение, ссылки и rendered results TIFF/JSON/пресетов 0.12.5; frozen fixtures и compact defaults v1 не менять.
- Временный SO документа не является старым compositor .asset форматом.
- Не объединять разные значения revision/save fingerprint/render stamp или разные контексты настроек кисти.
- Не менять UI appearance, Undo, source resolution, группы, Target, clipping и texture ownership.
- Каталог проверок и этот отчёт не расширяют разрешения на ассеты, настройки, Unity internal reflection, player build или push.

Начать с **R14**, затем **R05**, потом ограниченный **R09**. У каждой задачи должен исчезнуть конкретный повторный шаг сопровождения; если обязательных мест правки и проверок стало больше, извлечение не достигло цели.

Результаты предыдущих проверок не подтверждают будущие изменения. Commit/push и изменение версии в этом пересмотре не выполнялись.
