Исследование 2026-09-19. Unity 6000.7.0a6, Windows/DX12, текущий Editor проекта Test6.6.
Первоначальные замеры и план сохранены ниже как baseline. Часть оптимизаций уже реализована —

## Реализовано после исследования

Отдельное исследование маленьких документов (1–5 Drawing), с важным уточнением о различии

### Burst SHA-256 (2026-09-20)

`WhimTexSha256` заменяет только расчёт SHA-256 stored blocks при Save и проверке при Open.
Алгоритм/байтовый порядок/32-байтный digest прежние; версия контейнера не меняется.
Переносимый C# с uint-операциями, Burst direct call, без intrinsics, OS API или native DLL.
Обычные container worker threads вызывают ядро напрямую: дополнительного планировщика Jobs нет.
Последовательное состояние одного SHA-сообщения сохраняется между порциями, не заменяется tree hash.

- Scratch NativeArray: максимум 1 МиБ на вызов; при четырёх workers максимум 4 МиБ дополнительно.
  Даже крупный Drawing не требует полной дополнительной native-копии. Scratch освобождается через `using`.
- Блоки меньше 4 КиБ и отключённый Burst используют прежний `IncrementalHash`.
  Глобальная настройка Burst не изменяется. Для ядра включена синхронная компиляция при необходимости.
- Кеш, exact comparison, compression, атомарная запись, API и формат не изменены.

Изолированные измерения в том же Unity 6000.7.0a6, встроенный Burst 2.0, Windows Editor.
Время Burst **включает** выделение/освобождение scratch и копирование данных:

| Нагрузка | .NET SHA-256 | Burst SHA-256 |
| --- | ---: | ---: |
| 64 МиБ, три последовательных измерения | 2,901 / 2,820 / 2,840 с | 0,325 / 0,318 / 0,318 с |
| 4 независимых digest по 64 МиБ, параллельно | 4,660 с | 0,549 с |

Первый вызов из worker thread после reload — 5,49 мс на `abc`. Это **не** замер гарантированно
холодного Burst compiler cache. `BurstDiscard`-маркер подтвердил исполнение всех тестовых вызовов
в Burst, а не только наличие атрибута. Burst flags/safety settings не менялись.

Контейнерная проба `DocumentSaveCostProbe.Container([4,true])` до/после подключения:
четыре независимых opaque-random RGBA32 блока по 64 МиБ, первый вызов без cache hits:
**6,339 → 3,193 с**. Размер в обоих случаях 230225107 байт. Это `WriteTo` в counting sink:
compression + digest + выдача контейнера, **без** Compose, TIFF carrier, диска и импорта.
Повторы с 4/4 cache hits: до 0,560/0,592 с, после 0,487/0,447 с. На cache hit SHA уже не считается,
поэтому разницу повторов нельзя приписывать Burst. Полный 4K Save/Open заново не измерялся.

Проверки, все через подключённый Unity Editor:

- `DocumentBurstHashProbe.Run([64,3])`: **812** — известные SHA-256 векторы (включая million-a),
  все короткие длины 0–256 с ненулевыми offsets, padding/block/scratch boundaries, большие массивы,
  параллельные вызовы и факт Burst execution. Сравнение с .NET, без ассетов.
- `DocumentBurstIntegritySmoke.Run`: **32** — dispatch/fallback, независимый .NET-generated container,
  побайтно идентичная сериализация raw/compressed blocks, чтение и отказ при повреждении начала/середины/конца.
- `DocumentSaveCacheSmoke.Run`: **54** — кеш, ownership, mutation, Undo/Redo и Drawing.
- Компиляция Unity без ошибок, `git diff --check` пройден.

Новый тест/benchmark-код кроссплатформенный; фактически выполнен только Windows Editor / Burst 2.0.
Другие ОС, минимальный поддерживаемый Burst 1.8 и Player в этом этапе не запускались.
Fallback проверен прямым вызовом без переключения глобального Burst. Пользовательские сцены и
документы не изменены. Отчёт hash benchmark: `Temp/WhimTex/TiffValidationResults/burst-sha256.json`
от корня Unity-проекта (локальный артефакт, не файл пакета).

### Streaming и отмена (2026-09-20)

Приведённые в этом подразделе замеры выполнены **до** подключения Burst SHA-256.

Следующий этап: carrier больше не держит полные managed raw/converted/image массивы одновременно.
Он берёт native composite, конвертирует/сжимает до четырёх полос за раз и пишет их прямо в staging.
Проверка идёт bounded-пакетами со scratch-буферами; half conversion использует таблицы, Adler32 —
отложенный modulo. Streamed Open проверяет и распаковывает Drawing-блоки по одному с тем же
бюджетом raw+stored; соседние блоки больше не предзагружаются. Формат и значения пикселей не
изменены; explicit Precision — отдельная настройка.

При обычном открытии это также убирает прежнее окно предзагрузки четырёх блоков: сырой массив
живёт только до завершения `Texture2D.Apply`, после чего контейнер освобождает его до чтения
следующего слоя. Полностью ленивое открытие (создание Drawing-текстуры только при обращении к
слою) пока не включается: для него нужен отдельный lifecycle/Undo-контракт.

| 2048² × 3 | 1,838 мс | 262 мс | 1,582 мс | 473 мс | ~1 МиБ |

Оба прогона загрузили все слои, сохранили timestamp при no-op и прошли проверку формата.
Контрольный 4096² × 4 в этом же Editor завершился сбросом Pipeline на пике памяти, поэтому
его результат не считается валидным измерением; созданная пробой временная папка удалена.

завершается до освобождения памяти. Рендер/импорт/main-thread readback не стали асинхронными.

**Общее ускорение Save не доказано.** В повторных прогонах HDR Save колебался 6,2–12,1 с,

### Ранее: кеширование Drawing

- SHA-256 больше не вычисляется на сырых пикселях для поиска в кеше. Публичный native
  [Hash128.Compute](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Hash128.Compute.html)
  выбирает кандидата за 2,90–3,42 мс на 64 МиБ (три измерения).
- **Совпадение всегда проверяется побайтно**, без полной распаковки в память: 64-КиБ pooled
  buffer + streaming inflate. Изолированный замер на случайном opaque 4K — 378 мс.
  Поэтому даже коллизия fingerprint не может подменить пиксели. Новый счётчик ревизий Drawing
  не потребовался: прямые raw-записи без Apply, Undo/Redo, clear/fill и новые текстуры видны по данным.
- Immutable stored block содержит bytes, compression flag, raw length, SHA-256. Digest вычисляется
  один раз, остаётся прежним при reuse; сигнатура документа также использует этот SHA-256.
- Compression + digest новых блоков идут параллельно с ограничением до четырёх jobs и около
  256 МиБ одновременного raw input. Native snapshots освобождаются до Compose/carrier encoding.
- FIFO заменён на LRU; бюджет увеличен **192 → 256 МиБ**, чтобы четыре типовых 4K RGBA32 блока
  помещались без многогигабайтного кеша. Существует общий лимит 1024 entries. Несжимаемые raw
  блоки тоже кешируются. При eviction больше неиспользуемые записи не удерживаются моделью.
- Set копирует входной managed-массив; Get не отдаёт байты immutable cache напрямую. Повторное
  использование подготовленного digest запрещено для exposed mutable raw buffers.
- In-memory CreateEditableCopy пропускает compressed-cache lookup: независимые raw snapshots
  без ненужной распаковки. Внешние FX/dependency fast paths не расширялись.

### Что остаётся

No-op всё ещё O(суммарного объёма пикселей): fingerprint + точное сравнение, но без медленного
managed SHA-256. Первое сохранение и изменённый слой требуют настоящего compression/SHA-256.
Чтение файла по-прежнему проверяет целостность. Дисковый second-level cache, асинхронный Save,
тайлы Drawing, потоковая сборка TIFF strips и dependency tracking FX в эту оптимизацию не входят.
Есть measurable ускорение без этих усложнений; выбирать дальнейшую работу по реальным документам.

## Исходное исследование (до оптимизаций)

## Основной вывод

Главный расход — последовательное SHA-256 хеширование больших массивов дважды:
сырых пикселей для cache key, затем сохранённых блоков для integrity manifest.
Повторный Save не использует знание об отсутствии изменений пикселей; compressed cache
не хранит уже рассчитанный integrity digest. Это значительно дороже самого TIFF-кодирования.

В прежнем полном тесте 4×4096² RGBA32: первое сохранение 25,65 с, повторное без изменений
10,87 с, изменение одного пикселя 24,97 с. Из первого Save около 11,09 с — модель,
14,06 с — composite/carrier/container, 0,48 с — импорт. Это не четыре одинаковых слоя:
каждый содержит независимые случайные RGB и alpha=255. Такие данные сжимаются плохо;
гладкая или прозрачная кистевая работа даст другой результат.

## Изолированные замеры

`Tests~/DocumentSaveCostProbe.cs`, Unity Pipeline `run_script`, оптимизированная ephemeral-компиляция.
Проба не создаёт ассеты/сцены и не меняет открытые документы. Container пишет в счётчик
байтов без диска и импорта, поэтому результаты не являются замером полного Save.
Проба использует настоящий глобальный compressed cache: может вытеснить его содержимое,
но не очищает кеш вручную. Первичные пиксели и документы остаются нетронутыми.

| Операция | Объём | Время |
| --- | ---: | ---: |
| SHA-256 native span, два прогона | 64 МиБ | 2,657 / 2,701 с |
| SHA-256 managed buffer, два прогона | 64 МиБ | 2,677 / 2,651 с |
| SHA256.Create (`SHA256Managed`) | 64 МиБ | 2,663 / 2,658 с |
| SHA256CryptoServiceProvider | 64 МиБ | 2,633 / 2,675 с |
| NativeArray → managed byte[] | 64 МиБ | 4,56 / 4,42 мс |

Хеши всеми четырьмя SHA-256 путями совпали. Простая смена стандартного .NET API в этой
Unity не даёт аппаратного ускорения. Ни Windows-native SHA, ни другой алгоритм в продукт не добавлялись.
Время LDR TIFF в таблице не включает GPU readback/Compose, HDR→LDR conversion или HDR TIFF.

Контейнер без вычисления raw cache keys (ключи для пробы заранее уникально заданы):

| Блоки по 64 МиБ | Холодная запись | Повтор 1 | Повтор 2 | Cache hits до повторов |
| --- | ---: | ---: | ---: | ---: |
| 4 RGBA32 | 11,756 с | 11,227 с | 11,334 с | 3/4 |
| 3 RGBA32 | 9,426 с | 6,849 с | 6,910 с | 3/3 |

Четыре stored блока с каталогом занимают 230225107 байт (~219,56 МиБ), три — 172668520 байт
(~164,67 МиБ). Даже **полное попадание трёх блоков в кеш** оставляет почти 7 секунд:
сжатие пропущено, но SHA-256 последовательно считается снова. Для четырёх слоёв два прохода
SHA-256 дают ориентировочно 10,6 + 9,1 ≈ 19,7 секунды; это объясняет основную часть прежних
25,65 с, но не является точным распределением одного и того же end-to-end прогона.

## Неудачные места реализации

### 1. Кеш, для проверки которого надо перечитать все пиксели

`WhimTexDocumentSerializer.Writer.WriteTexture` синхронно хеширует каждый `GetRawTextureData`
до `TrySetCached`, даже при редактировании только имени, transform или другого слоя.
Fast path `WhimTexDocumentFile.Save` расположен **после** этого прохода. Поэтому no-op Save
не пишет файл, но платит 2,65 с на каждый 4K RGBA32 слой.

Нужен кеш raw digest по достоверной версии содержимого, а не по dirty всего документа.
Текущий `pixelsRevision` служит прежде всего URL provenance и не является полным счётчиком
содержимого: например `ClearSurface` не увеличивает его, а `PrepareStroke` увеличивает ещё
до изменения пикселей. Undo может вернуть старую версию; затем другая правка может снова
получить то же число. Использовать этот int как единственный cache key небезопасно.

`Texture.updateCount` также недостаточен. В пробе SetPixel изменил его с 0 на 2, Apply оставил 2,
запись через NativeArray без Apply изменила байт, но оставила счётчик 2. Для GPU-обновлений
Unity отдельно требует ручного увеличения счётчика:
[Texture.updateCount](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Texture-updateCount.html).
Нужны явные invalidation-точки для stroke end, fill, clear, replace/import, resize/HDR conversion,
CPU edits и Undo/Redo; native texture identity/layout и Unity counter — дополнительные проверки.
После reload или при неизвестном пути записи — безопасный пересчёт, не доверие устаревшему кешу.

### 2. Повторный integrity hash уже готового блока

`WhimTexDocumentContainer.WriteTo` выполняет compression параллельно, но затем вызывает
`Digest` в последовательном цикле каталога для **всех** блоков, включая `_reused`.
`Compressed` хранит bytes/flag/rawLength, но не digest.

Наиболее локальная оптимизация: immutable stored-block record с SHA-256, рассчитанным один раз
при создании блока. При cache hit использовать bytes + digest. При cache miss вычислять digest
в том же bounded worker job, что и compression, затем записывать каталог в прежнем порядке.
Формат и SHA-256 сохраняются. Нельзя мемоизировать digest произвольно изменяемого byte[]:
публичный `SetCompressed` сейчас принимает массив вызывающего кода без копии, а uncompressed
ветка может сохранить именно его. Сначала закрепить ownership/immutability.

### 3. Кеш ограничен памятью, но не предназначен для больших документов

- Глобальный лимит 192 МиБ: четыре тестовых блока занимают ~220 МиБ, один неизбежно вытесняется.
- FIFO, не LRU: попадание не делает блок более свежим. Несколько документов конкурируют.
- Pin через `_reused` защищает текущую запись от уже случившегося eviction, но не следующий Save.
- Несжимаемый native block: `Deflate` возвращает null (писать raw), cache entry получает bytes=null,
  `TrySetCached` отвергает его. Следующий Save вновь пробует сжать те же несжимаемые пиксели.
  Подтверждено на 1 МиБ случайного RGBA: cache miss; контрольный RGB+alpha255 даёт hit.
- Чтение файла проверяет stored SHA, но не сохраняет готовый block descriptor вместе с новым
  Texture2D для дальнейшего Save. После reload/open преимуществ ранее записанных блоков нет.

Просто поднять лимит до гигабайтов — не решение. RAM LRU полезен как ограниченный ускоритель;
основной fallback для неизменённых слоёв — уже записанные блоки предыдущего TIFF. Нужно привязать
их к валидированной ревизии файла и конкретному snapshot пикселей. Изменившийся внешний файл,
Save As, reorder слоёв и Undo не должны приводить к копированию неправильного блока.
При копировании с диска нельзя слепо доверять одному имени блока: нужна проверка источника/
целостности; её стоимость должна учитываться отдельно. Для первого Save такого источника ещё нет.

### 4. Любой FX выключает ранний no-op fast path

Serializer ставит `HasExternalInputs = true` на **любой** ShaderFX, не только на внешний preset/include.
Для таких документов Save проходит Compose, TIFF/container write и только в конце сравнивает
staging-файл с исходным. Это безопасная, но очень широкая консервативная защита.

Убирать её вслепую нельзя: внешняя текстура/HLSL/include может измениться без правки модели;
возможны зависящие от времени/глобального состояния эффекты. Нужна отдельная dependency signature
для доказуемо стабильных входов. Даже без неё кеш отдельных Drawing-блоков уже полезен.

### 5. Монолитные буферы и параллелизм увеличивают пиковую память

Container держит все snapshots и все compressed results до записи; каждый Deflate использует
растущий MemoryStream + ToArray. TIFF отдельно создаёт managed raw copy, преобразованный full-image
buffer, набор compressed strips и собранный file byte[]. Это не главный CPU-тормоз данного теста,
но накладывается на текстуры CPU/GPU, paint surfaces, Undo и сборщик мусора.
Предыдущий полный тест давал рост private committed memory всего Editor примерно на 2,5 ГиБ;
это не точный объём аллокаций одного writer и не GPU memory.

Нужны бюджет памяти на snapshot/jobs, ограничение числа одновременных крупных compression tasks,
потоковая выдача TIFF strips и block payloads в staging. Каталог требует длин блоков заранее:
reserve/patch directory или временный spool, а не удержание всех результатов в RAM.
Менять это после исправления лишнего hashing, не одновременно с форматом/Undo/Live lifecycle.

### 6. Дополнительные пути и неполная детализация тайминга

- `CreateEditableCopy` использует storage serializer: даже для in-memory клона платит raw hash,
  а при попадании compressed cache может распаковывать уже существующие исходные пиксели.
  При миграции старого `.asset` Save сначала делает эту копию, затем сериализует её ещё раз.
  Нужен режим snapshot/deep copy без storage compression lookup; независимость копии обязательна.
- Существующий лог начинает Stopwatch после Normalize/SyncDrawing/приостановки Live; `carrier`
  включает Compose. Для реального рисования добавить отдельные метрики этих стадий.
- В TIFF write Adler32 уже использует deferred modulo, но validate считает два `%` на каждый байт.
  Можно унифицировать checksum helper с сохранением проверки. На этой LDR-пробе вся validation
  занимает всего 60 мс — не приоритет и не основание её выключать.
- Полное сравнение временного файла с исходным остаётся полезным fallback. Оптимизация должна
  реже доводить no-op до этой стадии, а не убирать Flush/atomic replace/external-write guard.

## Предлагаемый порядок реализации

1. **Stored block + cached integrity digest**, безопасное владение bytes; параллельная обработка
   независимых блоков с ограничением ресурсов. Без смены формата. Это самый изолированный этап.
2. **Pixel content revision/cache** с проверкой всех путей изменения и Undo. Неизменённые Drawing
   не хешируются и не клонируются; неизвестный путь/reload пересчитывается. Небольшая модель
   сериализуется отдельно; надёжность no-op не должна зависеть только от UI dirty.
3. **Повторное использование stored blocks из файла**, корректный raw/uncompressed fallback,
   bounded RAM LRU; после этого streaming buffers. Не хранить в памяти все старые версии мазков.
4. **FX dependency fast path** и более дешёвое CreateEditableCopy. Это отдельные оптимизации,
   а не условие для исправления первых двух проблем.
5. При необходимости **асинхронный Save**: main-thread snapshot/render → background bytes work →
   main-thread import/bind. Snapshot revision важна: новые правки во время записи нельзя пометить
   сохранёнными. Одной фоновой задачей количество работы и расход памяти не уменьшаются.

Не обещать конкретное ускорение до повторного end-to-end benchmark. Первые два этапа направлены
на измеренные десятки секунд повторной работы; у первого Save останутся реальные hash/compression,
у изменённого слоя — стоимость его подготовки, у любого изменённого TIFF — запись нового файла.

Не начинать со смены TIFF, нового компрессора, отключения checksums/валидации, гигантского кеша
или обязательного тайлового формата Drawing. Тайл/чанк полезен для маленьких мазков на больших слоях,
но затрагивает формат, загрузчик, GC/Undo и требует отдельных замеров после дешёвых улучшений.

## Регрессии перед принятием оптимизаций

- Первый Save, no-op, transform/name-only, один пиксель в одном из четырёх 4K слоёв.
- Холодный/тёплый кеш, eviction, несколько документов, domain reload/open, Save As, reorder.
- RGBA32/RGBAHalf, прозрачные/плотные/несжимаемые данные; пиксели после round-trip совпадают.
- Stroke, clear, fill, URL replace, CPU edits, HDR conversion, Undo→другая правка→Save и Redo.
- Внешние texture/HLSL/include изменения, скрытые Drawing и FX references.
- Ошибка записи/импорта, отмена, внешний конфликт, Live pause/resume, GUID/.meta сохранность.
- Ограничить CPU/managed/private memory, измерять UI stall отдельно от total Save; не снимать
